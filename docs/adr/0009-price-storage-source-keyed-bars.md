# Price Storage: Source-Keyed Bars, Adjustment As Fetched

Status: accepted.

Context: `get_prices` returns a `FrameData` that is cached and discarded, so no price history is written down. ADR-0005 exists because adjusted history is rewritten by corporate actions, and the road map assumed the reconstructable answer was to store unadjusted prices plus a corporate-action record. Checked against the live API, that option does not exist. `yfinance` with `auto_adjust=False` returns `Open, High, Low, Close, Adj Close, Volume, Dividends, Stock Splits`, and the OHLC columns are already split-back-adjusted - NVDA traded near 1200 USD on 2024-06-05 and Yahoo reports 118.37 - so `auto_adjust=False` withholds only the dividend adjustment. Truly raw prices are not obtainable from Yahoo. Separately, CoinGecko's OHLC endpoint never returns daily candles: 7 and 30 days come back at 4-hour spacing, 90 and 365 days at 96-hour spacing, `days=max` requires a paid key, and the payload carries no volume. Its `market_chart` endpoint does give daily points with volume and market cap, but close-only.

Decision:
- Bars are stored as fetched, one current vintage, overwritten on re-fetch. A split rewrite scales every price before the split by one constant, so consecutive ratios are unchanged and the adjustment across the split date is exactly what makes that day's return correct. The rewrite that ADR-0005 guards against does not move returns; only the dividend adjustment does, and that is controlled by storing both `close` and `adj_close` side by side so price return and total return are both computable and neither convention has to be guessed at.
- Every bar carries `fetched_at`, so a vintage is identifiable even though only one is kept.
- Corporate actions are stored as their own rows, not as bar columns. They are events, they are overwhelmingly zero, and they are the only record of why history changed.
- A `Restatement` row is written when a re-fetch changes an already-stored bar by more than float noise and no corporate action explains it. Yahoo does occasionally correct bad ticks, and that is a silent rewrite which does move returns. One small table turns an invisible problem into a visible one, which is the reason ADR-0005 exists.
- A bar's key is `(instrument, source, bar_date)`. Source is part of the key, not a tiebreak, so two vendors disagreeing on a close each keep their row. Vendor disagreement becomes queryable rather than destructive, and is resolved at read time, not at write time.
- `bar_date` is the session date in the venue's own calendar. Yahoo already stamps bars in venue time - UTC for `BTC-USD`, `Asia/Tokyo` for `7203.T`, `America/New_York` for US equities - and CoinGecko's daily points land on 00:00 UTC, so the two vendors agree on what a crypto day is.
- No time-of-day is stored. A session close is a property of a venue's calendar, derivable from `Scope`, not a fact about a bar; if a lead-lag correction is ever wanted, an exchange-calendar table is its home and it can be added without touching stored bars.
- `Instrument` carries `identity_source`, a single value, and `price_sources`, an ordered preference. The first source holding a bar for a date supplies it, and the bar row records which one did. The list is ordered rather than singular because fallback is per date, not per instrument: Yahoo may carry a coin only from its listing date while CoinGecko covers the earlier stretch at lower fidelity.
- Crypto bars therefore come from Yahoo where Yahoo has the pair, and from CoinGecko `market_chart` otherwise, while identity and market cap always come from CoinGecko.
- A CoinGecko-sourced bar leaves `adj_close` null rather than mirroring `close`. Equal by coincidence and equal by definition should not look the same.

Considered Options:
- Bitemporal storage keyed on `(instrument, source, bar_date, fetched_as_of)`, every vintage retained. Perfectly reproducible, and storage multiplies every time a daily job re-fetches an overlapping range.
- Current vintage plus a corporate-action log presented as a reconstruction mechanism. Any earlier vintage is derivable, since splits are what rewrote it and the factors are held - but nothing is expected to use the reconstruction, so presenting it as a feature overstates it. The corporate-action table is kept for its own sake.
- Store only `Adj Close`. Smallest, and it permanently conflates price return with total return.
- One field for primary source, serving both identity and prices. Rejected once the CoinGecko granularity limits were measured: identity from CoinGecko and bars from Yahoo is the systematic case for every crypto instrument, not an exception.
- `bar_date` plus `session_close_utc`. One nullable column makes cross-market lag explicit, and it smears a calendar problem across the largest table in the schema.

Consequences: Bars on one `bar_date` are not contemporaneous - Tokyo's close precedes New York's by fourteen hours and crypto's UTC midnight sits between - so a covariance over a mixed universe correlates windows that do not overlap and systematically understates cross-market correlation. This is accepted, and is near-universal practice. A stored crypto series can be heterogeneous, with some dates carrying full OHLCV from Yahoo and others carrying a CoinGecko close with null open, high and low, so consumers must tolerate null OHL and rely on `close`. CoinGecko's free tier reaches back 365 days, so it can only ever backfill a recent window. `fetch_coin_ohlc` is unusable for daily history and `market_chart` is not yet wired into the adapter.
